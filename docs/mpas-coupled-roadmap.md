# MPAS ocean, sea-ice and land-ice: port roadmap

woof's hex lane is a port of MPAS-Atmosphere v8.4.2. The same MPAS-Model
snapshot (MPAS-Dev/MPAS-Model v8.4.2, `f34984b2c89353cf31c235b08d3b4acd96b37bb3`)
carries three more cores: `core_ocean` (MPAS-Ocean), `core_seaice`
(MPAS-Seaice) and `core_landice` (MPAS land-ice, MALI). This page records
what is ported from those three cores, how each piece is held to a reference,
and what remains.

## What existed before these cores

These are separate models. None of them is a port of the three cores, and the
cores do not replace them:

| Module | What it is |
|---|---|
| `woof/hex/mpasphys/seaice_v842.py` | MPAS-Atmosphere's sea-ice *surface* treatment (the Noah sea-ice module MPAS-A calls). It is atmospheric physics over a prescribed ice cover. |
| `woof/hex/mpasphys/oml_v842.py`, `woof/hex/ocean_mixed_layer.py` | MPAS-A's slab ocean mixed layer (WRF `module_sf_oml.F`). |
| `woof/ocean/seaice` | An original zero-layer thermodynamic sea-ice model (Semtner 1976) for the WRF lane. It contains no Icepack or MPAS-Seaice source. |
| `woof/ocean/mixed_layer` | WRF 4.6.1's 3-D PWP ocean and the Pollard mixed layer. |
| `woof/ocean/waves`, `woof/ocean/surge` | The wave and storm-surge models. |

## Doors and the coupling spine

`woof hex seaice|ocean|ice {status,options,verify}` reports each core's port
status, the pinned oracle and the strict recipe. It also lists every option
the core's `Registry.xml` declares (276 sea-ice, 248 ocean, 72 land-ice
options). The inventories are generated by `tools/mpas_coupled_options.py` and
pinned by the Registry's sha256.

`woof hex coupled` plans one wall clock for the coupled cores:

- the cadence must divide every component's timestep;
- the run length must be a multiple of the cadence;
- a flux channel must be conserved to the bit;
- a core that is not yet ported is refused by name.

A core is `ported` only when its dynamical core and every scheme run on the
GPU and its landing gate passes. Until then its status is `stub`.

## The reference

MPAS v8.4.2 builds in single precision by default (`Makefile`:
"single is the default"). The hex port pins that build. The new cores use the
same strict recipe:

- GNU Fortran, `-O0 -ffp-contract=off`;
- `RKIND` = 4 for the core's own `real(kind=RKIND)` arithmetic.

The Icepack-lineage column package (`core_seaice/column`, `ice_kinds_mod`'s
`dbl_kind`) is double precision whatever `RKIND` is, so a column-physics port
is double. On Metal that means woof's soft-f64. MPAS-Ocean is run in double
precision in practice, so its pieces are held at both RKIND 4 and RKIND 8.

Each piece is a *targeted extraction*. The routines are compiled verbatim and
checked against a `SOURCES.sha256`. The only stand-ins are the framework types
the routines walk (pools, blocks, timers), and those carry no arithmetic. A
driver feeds known inputs and writes the outputs as raw words. The
`mpas-oracle` pixi environment (`pixi run -e mpas-oracle ...`, linux-64)
supplies gfortran. Tests that need the oracle build skip by name when it is
absent, and committed fixtures under `tests/data/oracles/` keep the word
comparison running without it.

## MPAS-Seaice (`core_seaice`, about 99,000 lines)

Ordered by how self-contained each piece is:

1. **EVP internal stress, variational discretisation** (`shared/mpas_seaice_velocity_solver_variational.F`,
   `..._constitutive_relation.F`): strain tensor, EVP and revised-EVP
   constitutive relation, stress divergence, and `seaice_init_evp`. These are
   the inner loop of the elastic subcycle.
2. The rest of the elastic subcycle (`mpas_seaice_velocity_solver.F`). Ported:
   the Coriolis coefficient, ocean stress, subcycle initialisation, ocean
   stress coefficient, `solve_velocity` and `solve_velocity_revised`, and the
   principal stresses, composed with item 1 into whole subcycles; and the
   other pre-subcycle routines (mass and area aggregation, masks,
   `new_ice_velocities`, the Hibler `ice_strength`, `air_stress`,
   `surface_tilt`, with `seaice_mesh`'s cell-to-vertex interpolation) and
   `ocean_stress_final` (with its vertex-to-cell interpolation), so the whole
   of `seaice_run_velocity_solver` for the variational scheme. Still to port:
   the column package's ice strength (`colpkg_ice_strength`, refused by
   name). The column package is
   double, so production MPAS-Seaice is built double: each seaice piece is
   held at RKIND 4 and 8.
3. The basis-function setup for the variational solver (Wachspress and PWL,
   `..._wachspress.F`, `..._pwl.F`). This is init-time work and can stay on the host.
   Its outputs (`basisGradientU/V`, `basisIntegrals*`) are the inputs the
   kernels in item 1 read.
4. The weak-form solver (`..._weak.F`), an alternative velocity discretisation.
5. Incremental-remap advection (`mpas_seaice_advection_incremental_remap*.F`)
   and upwind advection.
6. Column physics (`column/`, colpkg): `ice_therm_vertical` (BL99 and mushy
   thermodynamics), `ice_therm_itd`, `ice_mechred` (ridging), `ice_shortwave`
   (delta-Eddington), melt ponds, `ice_atmo`. These are double precision.
7. Biogeochemistry (`ice_zbgc*`, `ice_algae`, `ice_aerosol`). Refused by name
   until ported.

## MPAS-Ocean (`core_ocean`, about 80,000 lines)

1. Tracer advection, standard and monotone (`mpas_ocn_tracer_advection_{std,mono}.F`).
2. The split-explicit time integrator's tendencies. Ported: `vel_coriolis`,
   `vel_vadv`, `thick_hadv`/`vadv`, `vel_pressure_grad` (all five
   `config_pressure_gradient_type` values, with the common-level Jacobian) and
   `vel_hmix` (del2, Leith, del4). The POM/SCRUM, diagonal and pseudo-flux
   Jacobians in `mpas_ocn_vel_pressure_grad.F` are private and no config
   reaches them in v8.4.2. The tensor hmix forms (`mpas_tensor_operations`)
   are refused by name. The forcing terms (bulk forcing, surface stress,
   explicit bottom drag, Rayleigh friction, thickness surface flux) and their
   composition into `ocn_tend_vel` and `ocn_tend_thick` are ported. Refused
   by name: land-ice fluxes, frazil, the RKIND 8 bulk wind stress (glibc's
   double `cos`/`sin` have no permissive equal), and the bottom drag or
   Rayleigh bottom friction on a mesh with a dry edge (v8.4.2 indexes level 0
   there). Still to port: `ocn_tend_tracer`, then the barotropic subcycle
   (`mode_forward/mpas_ocn_time_integration_split.F`).
3. Equation of state (`equation_of_state_jm`, `_linear`) and diagnostics.
4. Vertical mixing: constant and Richardson (`vmix_coefs_*`). CVMix (KPP) is
   an external library fetched by `get_cvmix.sh`; it is ported or refused by
   name.
5. GM and Redi (`mpas_ocn_gm.F`, `tracer_hmix_redi`), forcing, and land-ice
   fluxes.
6. Ecosystem/BGC tracers (`get_BGC.sh` externals). Refused by name.

## MALI (`core_landice`, about 22,000 lines)

1. The SIA velocity solver (`mode_forward/mpas_li_sia.F`), the default
   `config_velocity_solver`. `li_sia_solve` is the first target. Its edge loop
   is short, but its extraction is wider than the sea-ice or ocean ones:
   - It calls `li_calculate_flowParamA` (`mpas_li_thermal.F`), which needs
     `exp`.
   - It calls the barycentric vertex interpolation
     (`mpas_cells_to_points_using_baryweights`, `framework/mpas_geometry_utils.F`)
     or the kite-area one (`li_setup`).
   - It reads the `li_mask` bit tests.
   - It raises to real powers (`x**(n-1)`, `x**(n+1)` with a real
     `config_flowLawExponent`), which gfortran compiles to `powf`/`pow`.

   So the oracle compiles `li_constants`, `li_setup`, `li_mask`, `li_thermal`
   and `mpas_geometry_utils` verbatim, and the stand-ins grow to
   `mpas_timekeeping`, `mpas_log`, `mpas_abort` and
   `mpas_vector_reconstruction`. The GPU side takes `powf` and `expf` from the
   hex lane's qualified glibc transcriptions (`woof.hex.native_powf`,
   `glibc_flt32`). An RKIND 8 build needs a correctly matched double
   `pow`/`exp`; the LGPL glibc libm port stays behind its opt-in, so that
   precision waits for an MIT/BSD double `pow` that matches the oracle host.
2. Thickness and tracer advection (`mpas_li_advection.F`) and the
   forward-Euler time integration. The diagnostics advection reads (masks,
   geometry, layer thickness, layer velocity and its CFL step) are ported,
   and so is `li_advection_thickness_tracers` ('fo' and 'none', with and
   without tracers): `tracer_setup`/`tracer_finish`, the upwind advection,
   `apply_mass_balance` and `vertical_remap`. Still to port: the rest of the
   forward-Euler time integration.
3. The thermal solver (`mpas_li_thermal.F`): enthalpy/temperature column
   solves. Ported: the initialisation and the conversions, and
   `li_thermal_solver` (SIA heat dissipation, basal friction, the
   temperature and enthalpy matrix elements with `dsigmaTerm`,
   `tridiag_solver`, the conductive fluxes, grounded basal melt) with
   `li_basal_melt_floating_ice` ('none', 'file', 'constant', 'mismip',
   'seroussi'). The heat dissipation's zero row for an edge without two cells
   is ported but not reached by the oracle, whose masks need every edge's
   cells inside the mesh.
4. Calving, subglacial hydrology, masks and diagnostics.
5. **The Albany first-order (Blatter-Pattyn) Stokes solver**
   (`config_velocity_solver` = 'FO', also 'L1L2' and 'Stokes'). This is a C++
   finite-element code built on Trilinos (Kokkos assembly, NOX/Belos/MueLu
   nonlinear and linear solves), reached through
   `Interface_velocity_solver.cpp`. It is not part of MPAS-Model. A word-exact
   oracle needs a pinned Albany + Trilinos build. Even then, parallel
   multigrid and Krylov reductions are not bit-reproducible across
   decompositions, so the reference would be a single-rank,
   fixed-ordering build. Until that build exists, these solver values are
   refused by name. The FE pieces that can be pinned (element assembly of
   the FO viscosity and the basal friction residual) are the first
   candidates.
