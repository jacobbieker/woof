# Fast-TUV photolysis oracle, WRF v4.7.1

`build.sh WRF_SRC BUILD_DIR [FIXTURE_ROOT]` compiles chem/module_wave_data.F,
chem/module_ftuv_subs.F, chem/module_ftuv_driver.F and the modules they USE
(share/module_model_constants.F, chem/module_data_radm2.F,
chem/module_data_sorgam.F) whole and unchanged at `-O0`, against
`stub_ftuv.F90` (the Registry-generated index modules for the radm2 and
radm2sorg packages, and wrf_debug / wrf_message / wrf_abort).  It then runs
`run_ftuv.F90`, which calls `ftuv_init` once and `ftuv_driver` for five cases
on 6 x 2 columns of 30 levels, and writes one case per call through
`oracle_io.F90` (a byte copy of ../radm2/oracle_io.F90).

* `SOURCES.sha256` pins every compiled WRF file; a mismatch stops the build.
* NETCDF is left undefined.  It guards only the MOZART branches of
  module_ftuv_driver.F, which chem_opt = 1 and 2 never reach.
* Every -O0 object is checked for libmvec `_ZGV*` symbols, and a positive
  control proves the check can fire.
* Fixtures and provenance: `tests/data/oracles/chem/ftuv/`.  The port they
  grade is `woof/core/chem_ftuv.py` / `woof/core/kernels/chem_ftuv.cu`.  Its
  photo call tree is generated by `tools/chem_ftuv/transcribe_ftuv.py` from
  the same pinned sources.
